# 产品愿景与痛点

## 1. User Story【已确认】

> 我是一个全栈开发者。我会收到后端功能的 PRD、前端功能的 PRD、前后端夹杂在一起的 PRD，也会收到 Bug 修复任务。我在自己的 Windows 主机上开发和测试，使用 Codex、Claude Code、DeepSeek 等 Agent。我需要一个个人工单系统：创建工单，绑定前后端项目的目录或地址，连接本地 Agent，自动调度 Agent，并对 Agent 进行管理。

### 拆解后的子故事

| 编号 | 作为… | 我想要… | 以便… |
| --- | --- | --- | --- |
| US-1 | 需求接收者 | 把聊天里粘贴的、Word/PDF 里的 PRD 快速变成工单 | 不再在多个地方翻找需求 |
| US-2 | 需求把关者 | 在开发前让 AI 先帮我挑出 PRD 的漏洞、歧义和缺失 | 避免做到一半才发现需求不清 |
| US-3 | 需求把关者 | 修改 PRD 时保留版本，能看到每次改了什么 | 和需求方对齐、追溯 |
| US-4 | 全栈开发者 | 定稿后自动拆成前端 / 后端子任务，后端先出接口文档 | 前后端不打架，前端有契约可依 |
| US-5 | Agent 使用者 | 一键把子任务派给 Claude Code / Codex / DeepSeek，且可换用自定义 Provider | 不被官方渠道和单一模型绑定 |
| US-6 | Agent 管理者 | 实时看日志、随时停止、看耗时和 Token 花费 | Agent 失控时能及时止损 |
| US-7 | 代码负责人 | 每个工单在独立分支 / worktree 中进行，完成后看 Diff、跑测试、再决定是否合并 | 主分支始终干净，AI 改动可控 |
| US-8 | 验收者 | 验收不通过时写下意见打回，Agent 带着意见继续改 | 形成闭环，而不是重新开一个对话 |
| US-9 | Bug 修复者 | Bug 工单跳过 PRD 审核，直接进入开发 | 小问题快速处理 |

## 2. 痛点分析

| 痛点 | 现状 | 观澜的解法 |
| --- | --- | --- |
| **需求散落** | PRD 在聊天、文档、邮件里，Bug 在脑子里 | 统一入口：粘贴 / 文件导入 / 外部同步，全部转成 Markdown 工单 |
| **PRD 质量差** | 初版 PRD 常缺字段定义、异常流程、验收标准，开发中途返工 | AI 预审生成结构化问题清单 + 人工审核 + 版本化定稿 |
| **前后端割裂** | 混合需求要自己拆，前端常在接口未定时开工 | 定稿时拆分 FE/BE 子任务，后端先产出 API 文档，前端依赖其完成 |
| **Agent 会话难管理** | 多个终端窗口跑多个 Agent，忘了哪个在干嘛、谁花了多少钱 | 统一的运行面板：状态、日志、耗时、Token、停止 / 恢复 |
| **AI 改动风险** | Agent 直接改工作目录，改坏了难以回滚，多个任务互相污染 | 每个工单独立 git worktree + 分支，合并前人工 Review |
| **模型渠道受限** | 官方 API 贵或不可用，想用中转 / 国产模型 | Provider 作为独立配置，按工单 / Agent 选择，按进程注入环境变量 |
| **上下文重复输入** | 每次开 Agent 都要重新解释项目背景、规范 | 项目级"上下文卡片"+ Prompt 模板自动拼装 |
| **返工无闭环** | 验收意见要手动复制回 Agent | 打回意见自动作为下一轮运行的输入，并可恢复原会话 |

## 3. 设计原则

1. **本地优先**：数据、代码、密钥都留在本机；无需服务器即可完整使用。
2. **人在回路**：AI 负责"提议和执行"，人负责"定稿和合并"。PRD 定稿、代码合并两个关口必须由人确认。
3. **不侵入**：不修改用户的全局 Agent 配置（`~/.claude`、`~/.codex`），所有定制按进程注入。
4. **可观测、可中断**：任何 Agent 运行都能看到实时输出、随时停止、事后可追溯。
5. **可插拔**：Agent、Provider、工单来源、文档解析器都是适配器，便于后续扩展。
6. **先个人、后协作**：数据模型预留多人字段，但 MVP 只服务一个人。

## 4. 非目标（至少 V1 之前不做）

- 不做团队协作 / 权限体系 / 云端同步。
- 不自研 Agent 或代码生成模型，只编排现有 CLI Agent。
- 不替代 IDE；代码细节修改仍可在 IDE 中进行，观澜负责编排与追踪。
- 不做 CI/CD 平台；只在本地跑测试命令，不负责部署。
- 不支持 macOS / Linux 的官方打包（技术栈允许，但不承诺）。
