# 工单来源

## 1. 来源总览【已确认】

| 来源 | 形式 | 优先级 |
| --- | --- | --- |
| 手动创建 | 表单 + Markdown 编辑器 | P0 |
| 粘贴 | 整段粘贴聊天记录 / PRD 文本，支持粘贴图片 | P0 |
| 文件导入 | `.md`、`.txt`（P0）；`.docx`、`.pdf`（P1） | P0/P1 |
| 外部同步 | 飞书（文档 / 项目）、GitHub Issues | P2 |
| 【建议】剪贴板快捷创建 | 全局快捷键，把剪贴板内容快速建成草稿 | P1 |
| 【建议】本地接口 | 本地 HTTP / MCP，供脚本或 Agent 创建工单 | P2 |

所有来源最终都转换成 **Markdown 正文 + 附件**，作为 PRD v1。原始文件作为附件保留。导入的图片存为附件并在正文中引用，且只作参考，详见 [PRD 中的图片](prd-images.md)。

## 2. 智能创建【建议】

粘贴或导入后，可选运行一次轻量 AI 分析，自动填充：
- 标题、类型（后端 / 前端 / 混合 / Bug）
- 建议绑定的项目（根据关键词与项目上下文卡片匹配）
- 优先级、标签
- 若为 Bug：抽取复现步骤、期望、实际

结果仅作为表单预填，用户确认后才创建。

**现状**：粘贴 / 导入后先用本机规则预填（不联网）；用户点「AI 分析」才把正文和项目清单（名字、类型、上下文卡片摘要）发给设置里的默认 Agent。这次分析不给 Agent 任何读文件、跑命令的工具（Claude Code、Codex、OpenCode；Gemini CLI 和 Aider 没有对应开关，只是只读），在一个空目录里跑、最多等 3 分钟、可以取消，不建工单也不建 Run。回答里认不出的类型 / 优先级 / 项目会被丢掉，保留本机规则的判断；分析失败或回答不是约定的 JSON 时，右边仍是本机规则的结果。

## 3. 文件解析

| 格式 | 方案（候选） | 备注 |
| --- | --- | --- |
| Markdown / TXT | 直接读取 | 图片相对路径一并复制进附件目录 |
| DOCX | `mammoth`（JS）或 `pandoc` | 提取图片；表格转 Markdown 表格 |
| PDF | `pdf.js` / `pdfplumber` 提取文本；扫描件可选调用多模态模型 OCR | 版式复杂时质量有限，导入后建议走"AI 规整" |
| 图片（截图、原型） | 作为附件；可选让多模态模型生成文字描述 | 文字描述存入附件，供不支持图片的 Agent 使用；需求方贴的截图可标为权威图（见 [PRD 中的图片](prd-images.md)） |

解析器设计为插件接口：`parse(file) -> { markdown, attachments[] }`。

## 4. 外部同步（P2）

- **GitHub Issues**：通过 `gh` CLI 或 Token 拉取指定仓库、指定 label 的 Issue；Issue 正文为 PRD v1；评论作为时间线；可选在验收后回写评论 / 关闭 Issue。
- **飞书**：通过开放平台应用读取文档内容（docx → Markdown）或飞书项目工作项；需要用户自建应用并配置 App ID / Secret。
- 同步是**单向拉取为主**：外部更新时提示"源已变更"，由用户决定是否作为新 PRD 版本导入（若已定稿则走变更流程）。
- 记录 `source_url` 与 `source_rev`，避免重复导入。

### 4.1 实现现状（M4）

在「设置 → 外部同步」里添加来源。只在点「同步」/「导入」时联网，没有后台定时拉取。令牌和 App Secret 只进系统凭据管理器。

| 来源 | 做了什么 | 验证情况 |
| --- | --- | --- |
| GitHub Issues | 按仓库和 label 拉未关闭的 Issue 建成草稿工单（带 `bug` label 的建成 Bug，PR 跳过）；之后每次同步带上已关闭的；评论进时间线；正文或标题变了提示「源已变更」，可导入为新 PRD 版本（已定稿的先发起变更）或忽略；可选在工单完成后评论并关闭 Issue。令牌留空时用本机 `gh` 登录的账号。 | 只读拉取对真实的公开仓库跑过；回写只对本机的假接口测过。 |
| 飞书文档 | 用自建应用的 App ID / App Secret，按链接（`/docx/<id>` 或知识库 `/wiki/<节点>`）把新版文档转成 Markdown 建成草稿工单，图片作为参考图附上；「检查更新」比较文档版本号，有新版本时提示「源已变更」。 | **没有对真实的飞书验证过**：按开放平台文档写成，测试用的是照文档手写的响应。 |

没有做：飞书项目工作项、多维表格、旧版文档（`/docs/`）；GitHub 以外的 Issue 系统；外部评论的回复。

一次同步最多拉 500 个 Issue、给其中 60 个拉评论，避免第一次同步用完 GitHub 的请求额度。Issue 按更新时间从旧到新拉；到了上限就停在那里并提示「没有拉完」，再同步一次从停下的地方接着拉。

已经有工单的 GitHub 来源不能改成别的仓库（工单按 Issue 编号对应，换了仓库同一个编号是另一条 Issue）；要同步另一个仓库就新建一个来源。

## 5. 项目绑定

- 每个工单绑定一个或多个项目，并标注角色：`backend` / `frontend`。
- 项目可以是本地目录，也可以是 git URL（首次使用时 clone 到 `<工作区>/repos/<name>`）。
- 混合需求通常绑定一个后端项目 + 一个前端项目；Monorepo 可以同一项目同时担任两个角色，并分别指定子目录。
